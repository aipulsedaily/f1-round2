# The GitHub page itself — description, topics, and the pre-publication checklist

The repository page is the second thing a visitor reads after the search result
that got them there, and it is the one part of this project that no file in the
tree controls. This page holds the suggested text so it is version-controlled
and can be argued with, rather than typed into a web form once and forgotten.

**Everything here is a suggestion. The owner decides.**

---

## 1. Repository description

GitHub allows 350 characters and shows roughly the first 100–150 in search
results and social cards, so the load-bearing part goes first.

**Suggested:**

> A 124-second 4K film of an F1 car in one unbroken take, where every model,
> material and sound is generated by code — no downloaded assets, no HDRIs, no
> photo textures, nothing AI-generated. Ships its own engineering log: ~1,300
> entries recording what was measured and what turned out to be wrong.

*(283 characters.)*

**Shorter, if the first line is all that will be read:**

> A 4K short film built entirely from procedural code in Blender — one unbroken
> take, zero downloaded assets — published with the engineering log that records
> every measurement and every retraction.

**What the description should NOT do:** promise the film. The rendered master,
the frames and the audio are not in this repository and are not licensed for
reuse. A description that reads as "here is the film" sets up the one
disappointment this repository can actually cause.

## 2. Topics

GitHub allows 20. These are ordered by how likely each is to be the term
somebody actually searched for.

**Suggested (16):**

```
blender  blender-python  bpy  cycles  procedural-generation
procedural-modeling  3d-graphics  computer-graphics  rendering
animation  formula1  render-farm  gpu-rendering  audio-synthesis
engineering-log  reproducible-research
```

Notes on the two unusual ones:

- **`engineering-log`** is a small topic and that is the point. Someone browsing
  it is looking for exactly what makes this repository unusual.
- **`reproducible-research`** is defensible here in a way it usually is not:
  every asset is generated from source in the tree, and the log records the
  measurement behind each decision. It is *not* claiming the film is
  bit-reproducible on someone else's hardware.

Deliberately **not** suggested: `ai`, `machine-learning`, `generative-ai` — the
brief forbids AI-generated content anywhere in the pipeline and those tags
would say the opposite of the truth to a reader who never opens the README.

## 3. Social preview image

GitHub's Open Graph card is 1280×640. **This is currently blocked**, and it is
worth being explicit about why rather than shipping something weak:

- The repository tracks **four PNGs**, all of them pixel-peep crops from
  `work/r2226/` (before/after pairs at 2 MB and 190 KB). They are evidence
  attached to a specific entry, not presentation frames.
- Every full rendered frame is **gitignored and all-rights-reserved** — the
  licence carve-out in `LICENSE` §3 covers the frames as well as the encodes.

So a social preview needs the owner to **choose a frame and clear it**, which is
a licensing decision and not a formatting one. Two options:

1. **Publish one or two stills under a stated licence.** A hero frame from beat
   5 and a beat-1 assembly frame would do more for this repository than any
   amount of prose. This requires the owner to decide the frames are licensed —
   `LICENSE` §3 currently reserves all rights in every rendered frame, so the
   carve-out would need amending to name the released stills.
2. **Ship no social preview.** GitHub falls back to a generated card with the
   repository name and description, which is unexciting but not wrong.

**Recommendation: option 1, with two or three frames committed under
`docs/stills/` and named in `LICENSE` §3 as the exception.** The film's entire
claim is visual and the repository currently cannot show it. If the frames are
released, add them to the README's opening section too.

## 4. Repository settings worth setting

| setting | suggestion | why |
|---|---|---|
| **Default branch** | `main` | matches the links in `.github/ISSUE_TEMPLATE/config.yml` |
| **Issues** | on | the issue templates in `.github/ISSUE_TEMPLATE/` assume it |
| **Discussions** | off initially | the defect log is already the place where reasoning is recorded; a second venue splits it |
| **Wiki** | off | `docs/` is the wiki, in git, with the history that makes it worth reading |
| **Projects** | off | the film is finished; there is no roadmap |
| **Releases** | consider one tag | a `v1.0` marking the delivered master gives the repository a citable point without publishing the film |
| **Sponsor button** | owner's decision | — |
| **Security policy** | see below | — |

**A `SECURITY.md` is not included.** This repository ships no service, no
network listener and no dependency surface — it is scripts run locally by their
owner. The one credential-shaped risk it ever had is covered by §5 below and by
`docs/PUBLICATION-AUDIT.md`. If the owner would rather have the tab filled in,
a three-line file pointing at those two places is enough; a template security
policy promising a triage process nobody has agreed to run would be worse than
nothing, on the same grounds as everything else here.

## 5. Before the repository is made public

Ordered. Nothing below is optional except where it says the owner decides.

### BLOCKER — the vast.ai API key must be rotated

**This is not a documentation task and it cannot be closed by any amount of
scrubbing.** The key existed in plaintext on disk. A perfect scrub of every
tracked file, every historical blob and every commit message does not un-expose
a key that existed — it only stops it being *found here*. **Only the account
owner can rotate it, at vast.ai, and until that is done this repository must not
be published.**

Details, and what the scan actually found in the history, are in
[`PUBLICATION-AUDIT.md`](PUBLICATION-AUDIT.md).

### The checklist

- [ ] **Rotate the vast.ai API key.** Blocker. See above.
- [ ] **Decide the history question.** Three options, all still open because
      nothing has been rewritten: publish with history (~640 commits, personal
      addresses visible in most of them, all SHAs stable); `git filter-repo`
      with `--email-callback` **and `--message-callback`** (removes the
      addresses, changes every SHA, requires a mechanical remap of the 83 SHAs
      cited in 218 places); or a fresh single-commit init (removes the addresses
      and the provenance together). Each is priced in
      [`PUBLICATION-AUDIT.md`](PUBLICATION-AUDIT.md) §6, and
      `tools/publication/make_fresh_init.sh` builds the third so it can be
      compared rather than imagined.
- [ ] **Re-run the sanitiser.** `python3 tools/publication/sanitise_docs.py`
      — a dry run first. `tools/publication/README.md` explains why "run once,
      then trust" is not good enough for a corpus that is still being written.
- [ ] **Decide whether `tools/publication/` ships at all.** `alias_canon.txt` is
      82 real vast.ai identifiers and the sanitiser holds real host IPs;
      publishing them de-anonymises every `id-NNN` in the corpus. Deleting the
      map breaks the tool and the canary procedure that proves the tool can
      fail. **This is a disclosure decision, not a formatting one.**
- [ ] **Decide the three real vast.ai host IPs** in the sanitiser's own `IPS`
      table — `PUBLICATION-AUDIT.md` §4, "the sanitiser ships its own
      de-aliasing table". The companion `vast-render` repository has a larger
      version of the same question; keep the two answers consistent.
- [ ] **Decide on the untracked files.** Around 210 untracked-but-unignored
      files exist (`git ls-files --others --exclude-standard | wc -l`),
      including ten `docs/STAGING-*.md` and `docs/WAVE2-RANKING.md`. They are
      already sanitised in the working tree. Measured: publishing without them
      loses exactly **one** log entry (`R2-1661`) plus the ranking document, and
      leaves the corpus citing files it does not contain. See
      [`INDEX.md`](INDEX.md) §6.
- [ ] **Decide the licence.** GPL-3.0-or-later + CC BY-SA 4.0 is a
      *recommendation*, not a decision that has been taken. It can be changed
      now and cannot be recalled after the first public copy.
- [ ] **Decide the stills.** See §3 above. Affects `LICENSE` §3 if any frame is
      released.
- [ ] **Replace `OWNER`** in `.github/ISSUE_TEMPLATE/config.yml` with the real
      account name, and confirm the default branch matches those links.
- [ ] **Confirm the contact route** named in `CODE_OF_CONDUCT.md` exists.
- [ ] **Run the link check.** `python3 tools/docs_relink.py` must exit 0.
- [ ] **Read `README.md` as a stranger would.** It is the whole pitch and it
      gets about thirty seconds.

### After it is public

- The vast.ai key stays rotated. Do not put a new one on disk in plaintext.
- Any future commit uses a noreply address —
  `git config user.email 'ID+username@users.noreply.github.com'`.
- The sanitiser is re-run before each subsequent push, not once.
